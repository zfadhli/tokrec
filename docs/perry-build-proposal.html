Build proposal · packages/cli

tsdown out, Perry in

tsdown emits one JS file that only runs if the user has Bun. Perry compiles the same TypeScript into a native executable that runs if the user has nothing. That is not a bundler swap — it is a distribution-model swap, so this plan probes compatibility first, swaps the build second, and states plainly what npm users and the release matrix get instead.

Consequence

unbundle: true means the shipped file is a thin graph of .mjs modules that resolve npm deps at runtime on the user's Bun. Perry cannot consume that shape: it wants sources and it produces a binary. So the entry moves to src/bin.ts verbatim, and the dist/ tree stops existing.

02What Perry is

Perry is an ahead-of-time compiler, not a bundler. Rust host, SWC for parsing, LLVM 22 in-process for codegen, and a native stdlib that replaces the Node/Bun built-ins it claims to support. perry compile src/main.ts -o myapp writes a single self-contained executable — ~330 KB for hello world — with no engine inside.

What matters for this repo, from its own docs:

The "otherwise routed through an embedded V8" line is the one that decides whether this is worth doing: a dep left out of compilePackages keeps the JS runtime in the binary and forfeits the entire reason to compile. So the dep list is not an optimization — it is the acceptance criterion.

Target table trap

On Linux, Perry's --target linux is documented as a GTK4 executable. A CLI must never link GTK4. The headless options are --target linux-musl (fully static, "headless/server") and the explicit glibc linux-x86_64 / linux-aarch64. Which one produces a GUI-free binary is probe P0-1, not an assumption.

03Bidders: Perry vs scriptc

Two compilers claim the same job: TypeScript in, native executable out, no engine inside. They differ on the one axis this repo actually needs — whether the runtime APIs and npm packages it uses are inside or outside the supported subset, and what happens when they are outside.

What that means for this CLI

The CLI's non-JS dependency surface is exactly one line — import { Database } from "bun:sqlite" at src/browser-cookies.ts:9, used to read Firefox's cookie store. Perry implements that module; scriptc does not, and by design cannot fall back to an engine, so the whole build fails. Swapping the build tool would therefore mean rewriting Firefox cookie extraction on top of a pure-TS SQLite reader — a feature regression funded by a build-tool change. That settles the compiler choice on capability, not taste.

Decision

Perry. Not because it compiles better — scriptc's type-driven codegen is arguably the cleaner idea, and its automatic dependency compilation removes the compilePackages + allow-list ceremony entirely. Perry wins because this repo needs exactly one API that scriptc lacks, and because Perry degrades to an embedded runtime instead of refusing to build. Keep this section as the record of why the alternative was rejected.

One cross-check survives the decision: scriptc coverage packages/cli/src/bin.ts costs a single command in the same throwaway P0 branch and returns an independent verdict on which of the five deps are portable. If scriptc rejects execa too, the P2 rewrite is no longer a Perry quirk — it is a property of the code, and the ticket gets cheaper to justify.

04The fork

Perry produces executables. npm bin fields point at files inside the package. Those two sentences do not compose without a decision, and the decision is not reversible in a patch release.

A — keep a JS dist

Perry has no node-target JS emitter, so this means building with bun build and keeping the Bun shebang. Nothing is gained, and the CLI keeps requiring Bun on the user's machine. Rejected — it is a rename, not a refactor.

B — ship native binaries

@zfadhli/tokrec-cli becomes a launcher plus seven optionalDependencies platform packages, esbuild/Biome style. tokrec stops needing Bun, Node, or any runtime. This is the plan.

What option B costs, stated once:

  • Seven build artifacts instead of one — a CI matrix, not a single bun run build.
  • A 25–35 line JS launcher stays — npm still needs a JS bin entry to pick the right platform binary. It is committed, never built.
  • Release tooling grows — a script that stamps and publishes the platform packages before the launcher package.
  • Compiler becomes a build-time dependency — pinned, with perry doctor in CI and its object cache gitignored.

What option B buys, stated once:

  • packages/cli published with zero runtime dependencies — the five deps are compiled in.
  • Publish-order invariant dissolves for the CLI — the binary embeds the library, so @zfadhli/tokrec no longer has to exist on the registry before the CLI is published.
  • Bun requirement disappears from engines and from the shebang; npx tokrec works on a machine that has only Node for npm itself.
  • Cold start drops to process spawn — no engine boot for a 2-second --help.

packages/cli/bin/tokrec.mjs — the launcher (committed, not built) 
#!/usr/bin/env node
// Picks the platform package, hands over argv, and mirrors the child's exit.
import { spawnSync } from "node:child_process"
import { createRequire } from "node:module"

const require = createRequire(import.meta.url)
const libc = process.report?.getReport?.().header?.glibcVersionRuntime ? "" : "-musl"
const name = process.platform === "linux"
  ? `linux-${process.arch}${libc}`
  : `${process.platform}-${process.arch}`

let bin
try {
  bin = require.resolve(`@zfadhli/tokrec-cli-${name}/tokrec`)
} catch {
  console.error(`tokrec: no native build for ${process.platform}/${process.arch}${libc}`)
  console.error("tokrec ships linux, darwin and win32 builds — open an issue if yours is missing.")
  process.exit(1)
}
const { status, signal } = spawnSync(bin, process.argv.slice(2), { stdio: "inherit" })
if (signal) process.kill(process.pid, signal)
process.exit(status ?? 1)

spawnSync rather than spawn: tokrec is long-running and owns the terminal's signal handling itself, so the launcher must not become a second signal broker. Its only jobs are resolving, forwarding argv, and returning the child's status.

Scope note

The CLI's graph includes packages/tokrec/src, so a Perry build makes lib source changes unavoidable if execa fails. P1 is deliberately independent of Perry: it removes a runtime file read and shrinks the port surface, and it is revertible on its own. P3 and P4 are the point of no return and land as one commit or not at all — a half-swapped build is worse than tsdown.

08Gates

Every ticket, from the repo root, exit status checked — same discipline as the slimming series:

Non-negotiable

bun test stays on Bun and stays green throughout. Perry never runs the test suite — it compiles the CLI only. Tests exercising parseArgs, the option table, and the spinner keep running on the runtime they were written for.

09CI & release

Today publish.yml is one ubuntu runner: install, bun run build, publish lib, publish cli. After this plan the cli publish is downstream of a build matrix, and the lib publish is unrelated to it. 

# ci.yml — add one job
perry-check:
  runs-on: ubuntu-latest
  steps:
    - { uses: actions/checkout@v4 }
    - { uses: oven-sh/setup-bun@v2 }
    - run: bun install --frozen-lockfile
    - run: bunx perry doctor
    - run: bunx perry check packages/cli/src/bin.ts
# publish.yml — build matrix → 7 platform packages → launcher
strategy:
  matrix:
    include:
      - { os: ubuntu-latest,  target: linux-x86_64,   suffix: linux-x64 }
      - { os: ubuntu-latest,  target: linux-aarch64,  suffix: linux-arm64 }
      - { os: ubuntu-latest,  target: linux-musl,     suffix: linux-x64-musl }
      - { os: ubuntu-latest,  target: linux-aarch64-musl, suffix: linux-arm64-musl }
      - { os: macos-latest,   target: "",             suffix: darwin-arm64 }
      - { os: macos-13,       target: "",             suffix: darwin-x64 }
      - { os: windows-latest, target: "",             suffix: win32-x64 }

macOS and Windows rows build on their own hosts because Perry's Apple and MSVC paths want the platform toolchain; the four Linux rows cross-compile from one runner, including the fully static musl pair. Each row uploads a binary artifact; a final job runs scripts/pack-cli-platforms.ts, then publishes platform packages, then the launcher.

10Risks

#RiskLikelihoodResponse
R1 execa does not compile, and the lib's ffmpeg.ts also uses it — dragging a lib diff into a CLI build plan Medium P2: local spawn helper, per package commit, existing tests prove behaviour. Time-box the port attempt; do not patch node_modules.
R2 Linux binary links GTK4 or needs GUI libs at runtime Medium P0-1 decides the target per platform. Prefer linux-musl static; verify with ldd on the artifact, and run it in a bare debian:slim container.
R3 bun:sqlite compiles but the .query().all() / readonly shape differs at runtime Medium P0-3 smoke test against a fixture cookies.sqlite. Fallback: node:sqlite (also native) with a thin adapter.
R4 Perry ignores the "bun" export condition on the workspace lib and resolves dist/index.mjs Medium Harmless: restores lib-before-cli build order (already the rule today). P0-2 reports which it is; P6 documents the winner.
R5 Compiler churn — a Perry minor changes codegen and the binary regresses Medium Pin an exact @perryts/perry version in root devDependencies, commit bun.lock, and gate on perry check in CI so the upgrade is a deliberate PR.
R6 Binary size or cold start is worse than the Bun artifact Low P0-5 measures both. If it loses, the plan still holds on the runtime-dependency and publish-order wins — but say so in the CHANGELOG instead of claiming speed.
R7 Windows build fails on node:sqlite paths, cookie lookup, or MSVC Medium Windows is the last matrix row. If it fails, 0.16.0 ships six platform packages and the launcher prints the existing "no native build" message. Deferring Windows is acceptable; silently publishing a broken one is not.
R8 ANSI/spinner output differs between runtimes Low The --help diff gate catches it; the spinner is behind a tty check and a fake-spinner path in tests.

Non-goals

  • Compiling the @zfadhli/tokrec library to native. It stays a tsdown library with declared types.
  • Replacing bun test or perry dev as the dev loop. Perry builds cold in ~15 s; the dev loop stays bun run dev.
  • Homebrew, winget, or standalone GitHub binary downloads. They become easy once the matrix exists, and they are a separate decision.
  • Removing bun:sqlite from the lib's public surface. Nothing in the lib exports it.

11OPEN — your calls

#QuestionRecommendation
1 Native binaries for the CLI, or keep a JS dist and drop the Perry idea? Native. A JS dist means Perry buys nothing.
2 Perry or vercel-labs/scriptc? Perry — it implements bun:sqlite and degrades to an embedded runtime; scriptc refuses to build instead. If dropping Firefox cookie import is acceptable, scriptc becomes viable and its automatic dependency compilation removes the compilePackages bookkeeping entirely.
3 Windows in 0.16.0? Attempt it, publish it only if the matrix row is green. Do not block the release on it.
4 execa: probe first, or preemptively replace with a local helper? Probe first. Rewriting six working call sites on suspicion is the thing the slimming series just spent nine commits undoing.
5 Version: 0.16.0, or 1.0.0 since install requirements change? 0.16.0. Semver minor for a pre-1.0 build change; the breaking note goes in the CHANGELOG body, not the version.
6 Does P7 (live Ctrl+C remux check) gate the release? Yes. It is the one open item from the slimming series and the Perry binary is the honest place to finally run it.
7 Keep perry check in CI as a hard gate from P5, or advisory for a release or two? Hard gate. Advisory gates are how a V8 fallback ships.

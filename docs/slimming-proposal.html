Slimming proposal · packages/tokrec + packages/cli

Three bands, twenty-three modules

The A–D refactor bought correctness with structure: seven import bands, 33 library modules, and the same fact written three times. This plan keeps every behaviour and removes the scaffolding — seven bands become three, ten modules disappear, and the invariants the extra modules were supposed to carry move into the type system and a 60-line guardrail test.

01Diagnosis

The pattern

Every finding is the same shape: a module whose public surface is as wide as its body (F1, F2, F6) or a fact stored twice (F1, F3, F4). Neither costs behaviour — both cost reading time on every future change, which is the actual tax being paid here.

export function createRecorder(config: RecorderConfig): RecorderController {
  const cfg    = resolveConfig(config)          // app/config.ts
  const logger = createLogger({ ... })
  const events = createEvents()                // app/events.ts — typed node:events
  const status = { state: "idle" as Phase, user: cfg.user }   // no transition table (F6)

  async function start() {
    const scope = abortScope()                  // app/abort.ts, unchanged
    const post  = abortScope()                  // post-processing outlives Ctrl+C

    // built once, as consts — no module-level lets, no casts (F7)
    const http    = await createHttpClient(cfg)   // io/http.ts
    const client  = createTikTokClient(http, logger, cfg.debug, scope.signal)
    const monitor = createPollingMonitor({ intervalMinutes: cfg.interval, signal: scope.signal,
      onTick: () => tick({ client, monitor, scope, post }) })

    await monitor.start()
  }

  async function tick(d) {
    const verdict = await d.client.verdict(cfg.user)        // cached per tick
    const plan    = planTick(verdict, facts)                    // core/plan.ts
    switch (plan.kind) { /* poll · hold · record · stop(one-shot|gave-up) */ }
  }

  return { start, stop, getStatus: () => ({ ...status }), on: events.on, off: events.off }
}

05Candidates considered

ShapeResultVerdict
A — three bands core / io / app; merge by capability; keep one interface per live seam 23 modules · ~2426 lines · 3 concepts removed from the reader's head (bands, ports, pass-through downloader) chosen
B — flat, ten files drop bands entirely: tiktok.ts (~400), recorder.ts (~450), media.ts, config.ts… fewest files, but two modules over 400 lines, the "pure cannot touch network" rule becomes unreviewable, and the guardrail test has nothing left to check rejected — hides complexity instead of moving it
C — dedupe only keep all seven bands, apply D1–D11 27 modules · ~2500 lines rejected as the endpoint — does not fix F7/F9, and a 7×7 allow-matrix outlives its rationale

B and C are both defensible; the choice is A because the goal is a codebase a reader can hold, and the reader's cost is dominated by how many things have names, not by lines.

07Guardrail

test/architecture.test.ts is currently 155 lines to police seven bands; the source of the rework is the band count, not the test. Three bands let the whole rule fit in a table a reviewer can check by eye: 

const ALLOWED = {
  core: ["core"],
  io:   ["core", "io"],
  app:  ["core", "io", "app"],
} as const

const PURE = ["core"]   // no node:*, no bun, no transitive I/O

What the new guardrail must keep checking: (1) no edge outside the matrix, (2) no import cycle, (3) no node:*/bun import reachable from core/, (4) only index.ts is a public barrel. What it must gain: an assertion that core/ exports no functions that are called from only one place is not testable — so instead the review gate is the deletion ledger: any new module added under core/ or io/ needs a second caller or a fake in the same PR.

Why the band count was the bug

A 7×7 matrix cannot be reasoned about, so the answer to "where does this file go?" became "wherever the last refactor put something similar". The result is 55 lines of interfaces that assert nothing (ports/), a downloader that forwards nine arguments (session/stream.ts), and a state machine nothing can fail (recorder-state.ts). Three bands answers the placement question by itself.

08Limits, risks, non-goals

RiskMitigation
T6 (renames) is a large mechanical diff that could hide a logic edit.Separate commit, no body changes; review with git diff -M --stat and delta, expecting 100% similarity on moved files.
T2/T5 touch the discovery context type, which 253 lines of resolver tests reach into.Import-path-only edits; resolvers.test.ts must pass with unchanged assertions, no fixture edits.
Live verification of the Ctrl+C remux fix (2daf3ff) is still outstanding.Do it before T3 or T5, while session/index.ts still has its current shape, so a regression cannot be confused with a rename.
The architecture test is the only mechanical proof the shape holds.Rewrite it in the same commit as the renames (T6) and re-run it; an injected node:fs import into core/verdict.ts must fail it, as it does today.

Non-goals

  • No behaviour change. WAF headers, the rate limiter, ffmpeg reconnect flags, the 30 s startup timeout, the 10-minute remux grace, cookie seeding, and every error string stay as they are — they are the recordings that already work.
  • No public API change. Everything deleted is internal (ports/, discovery/*, session/*) — none of it is re-exported by index.ts. Optional fields on RecorderStatus stay even though nothing reads them yet.
  • No bundler or build change. The build chain stays lib → cli, dts stays off for the CLI, and the files/exports contract is untouched.
  • No test deletion beyond the six getRoomId call sites and the guardrail rewrite.
